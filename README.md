# Funded

Funded is an independent Solana launchpad in development. It is designed to launch through the genuine Float program and turn only the creator allocation into automatic USD payouts. There is deliberately no claim route, button, or manual withdrawal flow.

## Run the current build

Use Node.js 24.12 or later. No dependencies or credentials are needed for local draft mode.

```sh
npm test
npm start
```

Open http://127.0.0.1:3100. Drafts and token images are saved in local SQLite. Optional `FUNDED_READ_RPC` is a comma-separated list of approved HTTPS Solana RPC endpoints; it enables read-only finalized transaction and mint views. `FUNDED_DB` overrides the local database path. Do not expose this local server publicly. The web interface uses the dark-blue reference palette, the adapted wave-and-dollar icon, and DM Sans (observed among Float's loaded assets, not verified as the wordmark's exact typeface). Obtain permission and clear the mark/name before public commercial use; this is not a Float-endorsed product.

Implemented: responsive site, draft validation and persistence, wallet-address connection without signing, explorer transaction and mint reads, clearly inactive earnings/payout/liquidity views, integer-unit and balanced-journal storage, quote guard, destination settlement guard, and a receipt-driven payout state model tested with fixtures. No financial provider mutation or wallet provisioning is wired. No live or testnet transaction was submitted.

Run `npm run demo` for a **fixture-only** automatic payout from two below-minimum USDC receipts to two verified-in-simulation fills. The local queue batches only already-converted USDC for the same mint, payout rail, normalized handle, and consent reference; it keeps receipt membership, rejects replays, and enqueues the batch atomically when the minimum is met. It resumes after restart and backs off for unavailable routes, unfilled orders and under-minimum balances. It cannot sign or reach a provider. Production batching, asset conversion, and provider identity verification remain separate implementation gates.

## Integration findings

### Default launch path: official Float handoff

Use Float’s official launch form and set **Other wallet** to the dedicated Funded fee wallet. Treat Float’s documented routing as an upstream dependency; a historical sample proving payment to a separate wallet is not a launch prerequisite. Funded still has to record the selected wallet and match it to the launched mint before enabling intake. The local launch page links to Float’s official form but does not send draft data or submit anything. Use these operator-only commands with the same `FUNDED_DB` as the draft server:

```sh
npm run intake:float -- reserve <draft-id> <dedicated-fee-wallet>
npm run intake:float -- confirm <draft-id> <launch-signature> <launch-mint> <receiving-account> <operator-evidence-ref>
npm run intake:float -- observe <draft-id> <receipt-signature>
npm run intake:float -- review <draft-id> <receipt-signature> <reviewed-cycle-policy.json> <reviewed-source-vault>
npm run intake:float -- audit <draft-id>
```

- Set `FUNDED_EXPECT_GENESIS` for all commands except `audit`; chain reads also need one trusted `FUNDED_READ_RPC`. The operator must supply an existing wallet they are authorized to use and attest to the exact wallet selection in Float. The confirmation checks finalized mint visibility and looks for the mint, creator signer and Float call in the transaction, but does not decode the wallet selection or verify custody.
- Use the enrolled wallet address for native SOL or the specific receiving token account for SPL. The observation stores an exact finalized **net balance change**, not proof of fee origin. It requires a later slot than the launch and complete before/after balances. Wrapped SOL routed to an SPL account is not a native SOL observation. Unsupported or ambiguous movements cannot be credited.
- The optional review stores a policy match alongside the held observation when the existing narrow SPL verifier agrees. Neither step writes to the payout ledger or starts a conversion. No production attribution policy, signer, or payout provider is enabled. Keep this database and operator evidence private.

### Capture launch and fee-cycle evidence without signing

With one trusted Solana RPC configured as `FUNDED_READ_RPC`, run `npm run inspect:float -- <signature>`. Optionally set `FUNDED_EXPECT_GENESIS` to reject a different cluster. The command records finalized transaction bytes for top-level Float instructions and their inner calls, account flags and exact SPL token balance deltas. It deliberately never labels a transaction a proven launch or creator-fee payment; a CPI or token delta alone does not establish that. Do not include RPC keys in reports or commits.

Useful traces: a known successful Float launch with a distinct fee recipient, a fee cycle before graduation, and a fee cycle after graduation; the launch and fee traces should belong to the same mint. Include both SOL and a non-SOL pairing. Use the expected receiver and mint addresses to reconcile the traces. A supported Float SDK/IDL or authoritative account map is preferable to guessing instruction offsets. The [Raydium LaunchLab instruction reference](https://docs.raydium.io/products/launchlab/instructions) documents the inner launch platform and is not a substitute for the Float wrapper ABI.

### Review a launch submitted through Float

Float constructs the launch. If a reviewed instruction policy is available, this optional tool checks the finalized instruction against it. Run `npm run review:float -- <reviewed-policy.json> <signature> <mint> <creator> <fee-receiver>` with one trusted `FUNDED_READ_RPC`. The policy fields are `genesisHash`, `fromSlot`, `throughSlot`, `discriminatorHex` (8 bytes as hex), `accountCount`, and zero-based `roles` (`mint`, `creator`, `feeReceiver`). Only populate these from reviewed Float instruction semantics tied to a known deployed version and slot range. No live policy ships; test policies are synthetic. Layouts that encode the recipient in instruction data or elsewhere are intentionally unsupported by this reviewer.

The command rejects a mismatched cluster, an out-of-scope slot, wrong or ambiguous instruction, mismatched recipient, or missing signer/inner LaunchLab evidence. A match proves consistency with the supplied policy, not that the policy is authoritative, that fees were paid, or that a payout can proceed. Finalized receipt reconciliation, asset conversion and live payout permissions remain separate gates.

### Review a candidate creator-fee receipt

Run `npm run review:float-fee -- <reviewed-cycle-policy.json> <expected-route.json> <signature>` with one trusted `FUNDED_READ_RPC`. The policy pins the `genesisHash`, reviewed `fromSlot` / `throughSlot`, 8-byte `discriminatorHex`, exact `accountCount`, and `roles` (zero-based `launchMint`, `sourceVault`, `destination` instruction account positions). Its `stage` (`bonding` or `graduated`) labels the reviewed policy, not an independently observed pool state. The expected route separately pins `launchMint`, `feeMint`, `feeReceiver` (destination token-account owner), `sourceVault`, and `destination`. Derive route addresses from trusted enrollment and reviewed on-chain state, not the incoming transaction.

This first version only accepts an isolated direct legacy SPL Token `transferChecked` CPI. It checks source, mint, receiving account and owner, program, and exact integer balance change. Native SOL, Token-2022, plain transfers, nested or ambiguous CPIs, and missing balance metadata fail closed. A match provides a deterministic evidence reference, not permission to credit the ledger or pay out. No production cycle policies are bundled; compare finalized traces for each supported phase and asset before onboarding them.

To find candidates without knowing a transaction signature, run `npm run discover:float -- <wallet-or-token-account> [before-signature]` with one trusted `FUNDED_READ_RPC` and a pinned `FUNDED_EXPECT_GENESIS`. This reads one page of finalized signatures and checks returned transaction identities, displays top-level Float instruction discriminators and the selected account's token deltas, and withholds the next cursor if any transaction is unavailable or inconsistent. Query the receiving token account as well as its wallet if only the token account is referenced. The command does not claim complete archival coverage and cannot record credit.

**Observed November 9, 2026:** [Float's official docs](https://www.floatlaunch.xyz/docs#fees) describe a 5% creator share of the amount remaining after Raydium's share, paid in the pairing asset to the wallet chosen at launch, before and after graduation. The [official launch form](https://www.floatlaunch.xyz/create) presents an **Other wallet** option. A [finalized PIRATE fee-cycle transaction](https://solscan.io/tx/4qspX9HzQ5ZPPvKb4Wz9eock565x58VGZVCy2JZJkXgTKVeb6HUL7LW7tix1xXmp6eGHgMYoofVKdERgYurAxn2u) at slot 467396472 shows two top-level Float instructions, a Raydium CPMM creator-fee collection CPI, and multiple WSOL transfers. This established that a transaction can contain more than one Float instruction; the checker now requires exactly one match to the reviewed discriminator and isolates the recipient from all other instructions. This observation does not identify a verified independent creator-fee destination or establish a production account map. The inner Raydium fee collection itself must not be counted as a creator payout.

- **Float:** [An indexed finalized Solana trace](https://scan.codex.io/sol/tx/2FqLr7FFsnsACbx7gUvqE3f3J2TGR4Sbz4uZUSYbE5LGwi2FmskHs6BZ9iHZDTyEuK9nttLJ4ihdN4PVWuxMbtsY) shows Float invoking Raydium LaunchLab on a trade. [FloatFuse](https://floatfuse.fun/docs/) describes an independent launch path and alternate recipient routing; [xFloat](https://xfloat.app/) describes a separate claim-based design that Funded does not want. These are corroboration, not validation of Funded's own instructions. The official documentation and launch form were verified in the browser as noted above. The brief's 15/5/35/35/10 allocation, alternative fee receiver, and 1/2/2.5% tiers are reference values, not executable configuration. Third-party fee labels conflict. Before enabling independent transaction construction or signing, obtain a trustworthy Float instruction schema or independently decode finalized known-good initialize transactions; confirm discriminator, signer/allowlist restrictions, exact accounts, current program data/upgrade authority, quote mint and tier encoding, first-buy cap, creator receiver or receiver ATA, and required privileges. This additional validation applies to native integration, not to launching through Float’s official form. Do not substitute a Raydium-only launch.
- **Peer:** [Peer Cash SDK source](https://github.com/zkp2p/peer-cash) documents X Money USD, Cash App and Venmo payout methods, supported input discovery, unsigned Base-only order preparation, deposit/fill reads and recovery. Depositing canonical Base USDC creates an order, not a USD payment. A matched buyer/LP sends fiat through the selected app; the proof and settlement determine status. Verify live USD capability, limits, buyer activity, proof requirements and terms for this third-party automatic payout model before enabling any rail. X Money handle normalization is not an eligibility check. Verify account ownership/consent, X Money activation and hosted receipt access where required. Cash App and Venmo are separate provider-validated payees; enable only a creator-approved fallback. Public SDK access does not prove a private partnership is needed, nor does it waive production permissions. [Peer's Solana contracts](https://github.com/zkp2p/zkp2p-solana-contracts) are not evidence that Peer Cash X Money can settle directly on Solana.
- **Conversion:** [Jupiter Swap Build](https://developers.jup.ag/docs/swap/build) provides a route/instruction candidate. Allowlist Float quote mints by address, token program, extensions, authority risks and transfer restrictions. Do not use ticker matching. Probe exact input, verify quote time, market depth, output floor, permitted programs, accounts, net transfer fees, payer and fee caps; decode and simulate the assembled message before an isolated signer may approve. No safe route means pending in the original asset. All Float pairing mints are in scope for onboarding; availability to launch and availability to liquidate are separate gates.
- **Bridge:** [Circle CCTP](https://developers.circle.com/cctp/concepts/supported-chains-and-domains) lists Solana and Base. Use native Solana USDC into canonical Base USDC, evaluating standard CCTP first. Persist source burn and message identity, verify attestation and finalized matching destination mint/recipient/amount; recover the same message on delay, never issue another burn for uncertain submission. Evaluate a separately qualified fallback, not silent rerouting.
- **Economics:** Peer Cash documents zero-spread oracle pricing rather than custom LP spreads; zero spread does not make an end-to-end payout free. [BagsPay's guide](https://docs.bags.fm/how-to-guides/pay-fees-to-x-money) could not be retrieved directly; its thresholds and discounts from the brief are unverified references. Measure fill latency, calculate batch minimum from conversion, bridge and gas overhead, and show actual cost and fiat. If explicit LP incentives are required, validate a supported lower-level protocol configuration or a separately funded incentive; never imply the Cash SDK supports a custom discount or quietly lower recipients' USD.

## Read-only payout preflight

Run `npm run preflight -- swap <private-input.json>` to inspect a Jupiter Swap V2 exact-input quote for an approved pairing asset. Input fields are `asset` (`native:sol` or a mint address), `units` (integer string), `taker` (public Solana address), and `policy` (`assets`, `pools`, `topLevelPrograms` arrays, numeric `slippageBps`, `maxImpactBps`, `maxAgeMs`, and string `referenceMinNet` in USDC base units). An optional `FUNDED_JUPITER_API_KEY` is sent only to Jupiter. The check accepts only one approved pool with no added tip; liquidity can change and multi-hop routes remain on hold. It does not decode or simulate instructions, expose an unsigned transaction, or establish that a quote will settle.

Run `npm run preflight -- bridge <private-input.json>` to check an **existing** Solana USDC burn using [Circle Iris](https://developers.circle.com/api-reference/cctp/all/get-messages-v2). Input fields are `signature`, `senderProgram`, `baseMessenger`, `sourceWallet`, `baseRecipient`, `burnUnits`, `maxFeeUnits`, and `minimumNetUnits`. Pin these independently before looking up the burn; do not copy them from the response. The check accepts one standard, no-hook, unrestricted-caller Solana-to-Base message matching the pinned fields and fee limits. It does not verify attestation signatures or destination minting. A missing message is not authorization to re-burn. Exit code 2 means pending/held; exit code 1 means the request was invalid or failed to run. Neither command updates the ledger or sends a transaction.

## Production architecture

1. **Web and authorization:** React/Next.js web and TypeScript API are the target. Authenticate creator access with a short-lived, origin-bound Solana challenge. Separate the launch signer from the payout recipient. Use an expiring recipient consent flow, immutable payee IDs when available, and versioned rail preferences. Changing payee requires re-verification, an audit event and a hold; never change the destination of an existing order. One-time provider onboarding is not a fee claim. No public claim endpoint.
2. **Launch and fees:** Use Float’s official handoff as the default. After creator verification, assign a segregated receiving wallet per launched mint and record the approved wallet and expected pairing asset. Reconcile individual finalized receipts against that enrollment, recording the source, exact amount and a unique transaction locator so a receipt can be credited only once. A balance increase alone is not evidence of creator fees; hold unrelated or ambiguous transfers for review. No claim step is added.
3. **Custody:** begin only after a licensed/approved custody structure is cleared. A restricted operator signing service holding a receiver key still controls funds. Prefer a qualified custodian or policy-controlled segregated addresses with scoped signing, dual approval on policy changes and recovery, immutable audit trail, replay protection and per-asset caps. Web servers cannot sign. Privileged operator recovery handles frozen assets/failed orders without a creator claim portal. Rights, return policy and who bears costs must be explicit.
4. **State and durable workers:** PostgreSQL in production, immutable journals and chain evidence, append-only reconciliation history, unique source locators, transactionally coupled outbox, bounded worker leases, fenced attempts and operation IDs. State path: finalized fee receipt → waiting for route or verified Solana USDC → pending bridge → verified Base USDC → pending Peer deposit → awaiting buyer → partial or paid; unused funds can return to Base and be retried automatically. Use claim-independent batching per approved recipient and payout preference, with immutable per-token allocations and rounding reconciliation. Neither unsigned quote, transaction submission nor buyer matching is payment evidence.
5. **Recovery and observability:** persist signed transaction identity before broadcasting when possible. On timeout, look for the exact signature/nonce, balance deltas, finalized events, order ID and message hash before retry. Retry observations independently of mutations. Poll from finalized cursors after restart; quarantine inconsistencies. Pauses block new signing but not polling/reconciliation. Alert on stale stages, route cost spikes, program upgrades, solvency drift, proof and order outages. Require restore drills, maker-signer limits, reconciliation reports and independent audit before production.
6. **Go-live gates:** verified launch-to-wallet enrollment and finalized receipt reconciliation; simulated conversion, bridge and amount checks; credentialed Peer preproduction tests for available rails and refunds; approved partner/custody model; qualified review of applicable [FinCEN guidance](https://www.fincen.gov/sites/default/files/2019-05/FinCEN%20Guidance%20CVC%20FINAL%20508.pdf), state laws, [OFAC guidance](https://ofac.treasury.gov/recent-actions/20211015), X Money/other app terms, tax/reporting and tokenized-asset restrictions; audit, monitoring and explicitly authorized low-limit live tests. [X Money](https://money.x.com/en/i/faq) also has its own eligibility and rollout limits.

For the funded flow, verified direct USD through X Money is the first acceptance test. Then verify Cash App and Venmo independently. Preserve funds and retry automatically on no liquidity, no route or outage. Never send to another rail without prior consent.

### Public release criteria

Keep payout enrollment and financial writes closed until there is evidence for each applicable gate. A local fixture, provider capability listing, quoted amount, or attestation response is not a release sign-off.

| Gate | Required evidence before enabling |
| --- | --- |
| Fee intake | Approved wallet custody and recovery, and reconciliation of attributed receipts for each supported asset and fee route |
| Swap and bridge | Allowlisted instruction/account simulation, exact finalized source and destination settlement, and replay-safe recovery without double submission |
| USD payouts | Approved business use, authenticated payee and recorded consent, credentialed Peer preproduction order/fill/refund tests, and an explicitly authorized capped live test that reaches verified USD on each enabled rail |
| Public operation | Approved production infrastructure, authentication and privacy controls, financial/compliance and brand review, independent security review, tested monitoring, restore and pause procedures |

Brand assets are in `public/funded-mark.png` (full-resolution transparent source) and `public/funded-mark.webp` (web-optimized delivery asset).
