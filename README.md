# Funded

Funded is an independent Solana launchpad in development. It is designed to launch through the genuine Float program and turn only the creator allocation into automatic USD payouts. There is deliberately no claim route, button, or manual withdrawal flow.

## Run the current build

Use Node.js 24.12 or later. No dependencies or credentials are needed for local draft mode.

```sh
npm test
npm start
```

Open http://127.0.0.1:3100. Drafts and token images are saved in local SQLite. Optional `FUNDED_READ_RPC` is a comma-separated list of approved HTTPS Solana RPC endpoints; it enables read-only finalized transaction and mint views. `FUNDED_DB` overrides the local database path. Do not expose this local server publicly. The web interface uses the dark-blue reference palette, the adapted wave-and-dollar icon, and DM Sans (observed among Float's loaded assets, not verified as the wordmark's exact typeface). Obtain permission and clear the mark/name before public commercial use; this is not a Float-endorsed product.

Implemented: responsive site, draft validation and persistence, wallet-address connection without signing, explorer transaction and mint reads, clearly inactive earnings/payout/liquidity views, integer-unit and balanced-journal storage, quote guard, destination settlement guard, and a receipt-driven payout state model tested with fixtures. No financial provider mutation or wallet provisioning is wired. No live or testnet transaction was submitted.

Run `npm run demo` for a **fixture-only** automatic payout from fee receipt to two verified-in-simulation fills. The local dry-run queue persists a single authorized destination per receipt, applies transitions and queue updates atomically, resumes after restart, and backs off for unavailable routes, unfilled orders and under-minimum balances. It cannot sign or reach a provider. In this build the simulator does not combine receipts, so small balances remain pending; production batching and provider identity verification remain implementation gates. The launch draft supports all three payout preferences but does not enroll an account.

## Integration findings

- **Float:** [An indexed finalized Solana trace](https://scan.codex.io/sol/tx/2FqLr7FFsnsACbx7gUvqE3f3J2TGR4Sbz4uZUSYbE5LGwi2FmskHs6BZ9iHZDTyEuK9nttLJ4ihdN4PVWuxMbtsY) shows Float invoking Raydium LaunchLab on a trade. [FloatFuse](https://floatfuse.fun/docs/) describes an independent launch path and alternate recipient routing; [xFloat](https://xfloat.app/) describes a separate claim-based design that Funded does not want. These are corroboration, not validation of Funded's own instructions. Direct retrieval of [Float's documentation](https://www.floatlaunch.xyz/docs) and [launch form](https://www.floatlaunch.xyz/create) was unavailable. The brief's 15/5/35/35/10 allocation, alternative fee receiver, and 1/2/2.5% tiers are reference values, not executable configuration. Third-party fee labels conflict. Before enabling launch, obtain a trustworthy Float instruction schema or independently decode finalized known-good initialize transactions; confirm discriminator, signer/allowlist restrictions, exact accounts, current program data/upgrade authority, quote mint and tier encoding, first-buy cap, creator receiver or receiver ATA, and required privileges. Verify finalized fee cycles with a different recipient, before and after migration, on SOL, native USDC, and representative restricted or Token-2022 mints. Only enable each verified path. Do not substitute a Raydium-only launch.
- **Peer:** [Peer Cash SDK source](https://github.com/zkp2p/peer-cash) documents X Money USD, Cash App and Venmo payout methods, supported input discovery, unsigned Base-only order preparation, deposit/fill reads and recovery. Depositing canonical Base USDC creates an order, not a USD payment. A matched buyer/LP sends fiat through the selected app; the proof and settlement determine status. Verify live USD capability, limits, buyer activity, proof requirements and terms for this third-party automatic payout model before enabling any rail. X Money handle normalization is not an eligibility check. Verify account ownership/consent, X Money activation and hosted receipt access where required. Cash App and Venmo are separate provider-validated payees; enable only a creator-approved fallback. Public SDK access does not prove a private partnership is needed, nor does it waive production permissions. [Peer's Solana contracts](https://github.com/zkp2p/zkp2p-solana-contracts) are not evidence that Peer Cash X Money can settle directly on Solana.
- **Conversion:** [Jupiter Swap Build](https://developers.jup.ag/docs/swap/build) provides a route/instruction candidate. Allowlist Float quote mints by address, token program, extensions, authority risks and transfer restrictions. Do not use ticker matching. Probe exact input, verify quote time, market depth, output floor, permitted programs, accounts, net transfer fees, payer and fee caps; decode and simulate the assembled message before an isolated signer may approve. No safe route means pending in the original asset. All Float pairing mints are in scope for onboarding; availability to launch and availability to liquidate are separate gates.
- **Bridge:** [Circle CCTP](https://developers.circle.com/cctp/concepts/supported-chains-and-domains) lists Solana and Base. Use native Solana USDC into canonical Base USDC, evaluating standard CCTP first. Persist source burn and message identity, verify attestation and finalized matching destination mint/recipient/amount; recover the same message on delay, never issue another burn for uncertain submission. Evaluate a separately qualified fallback, not silent rerouting.
- **Economics:** Peer Cash documents zero-spread oracle pricing rather than custom LP spreads; zero spread does not make an end-to-end payout free. [BagsPay's guide](https://docs.bags.fm/how-to-guides/pay-fees-to-x-money) could not be retrieved directly; its thresholds and discounts from the brief are unverified references. Measure fill latency, calculate batch minimum from conversion, bridge and gas overhead, and show actual cost and fiat. If explicit LP incentives are required, validate a supported lower-level protocol configuration or a separately funded incentive; never imply the Cash SDK supports a custom discount or quietly lower recipients' USD.

## Production architecture

1. **Web and authorization:** React/Next.js web and TypeScript API are the target. Authenticate creator access with a short-lived, origin-bound Solana challenge. Separate the launch signer from the payout recipient. Use an expiring recipient consent flow, immutable payee IDs when available, and versioned rail preferences. Changing payee requires re-verification, an audit event and a hold; never change the destination of an existing order. One-time provider onboarding is not a fee claim. No public claim endpoint.
2. **Launch and fees:** use a pinned audited Float transaction builder; show mint, quote, fee receiver, cap, and all instructions before the creator signs. Generate the receiving account only after account verification. Use one segregated receiver per launched mint for attribution and avoid relying on a shared-wallet balance. Finalized polling plus slot-range backfills and indexed instruction/event evidence must prove both Float provenance and creator-share origin before crediting; quarantine unrelated transfers. Reconcile pre/post-graduation pathways independently.
3. **Custody:** begin only after a licensed/approved custody structure is cleared. A restricted operator signing service holding a receiver key still controls funds. Prefer a qualified custodian or policy-controlled segregated addresses with scoped signing, dual approval on policy changes and recovery, immutable audit trail, replay protection and per-asset caps. Web servers cannot sign. Privileged operator recovery handles frozen assets/failed orders without a creator claim portal. Rights, return policy and who bears costs must be explicit.
4. **State and durable workers:** PostgreSQL in production, immutable journals and chain evidence, append-only reconciliation history, unique source locators, transactionally coupled outbox, bounded worker leases, fenced attempts and operation IDs. State path: finalized fee receipt → waiting for route or verified Solana USDC → pending bridge → verified Base USDC → pending Peer deposit → awaiting buyer → partial or paid; unused funds can return to Base and be retried automatically. Use claim-independent batching per approved recipient and payout preference, with immutable per-token allocations and rounding reconciliation. Neither unsigned quote, transaction submission nor buyer matching is payment evidence.
5. **Recovery and observability:** persist signed transaction identity before broadcasting when possible. On timeout, look for the exact signature/nonce, balance deltas, finalized events, order ID and message hash before retry. Retry observations independently of mutations. Poll from finalized cursors after restart; quarantine inconsistencies. Pauses block new signing but not polling/reconciliation. Alert on stale stages, route cost spikes, program upgrades, solvency drift, proof and order outages. Require restore drills, maker-signer limits, reconciliation reports and independent audit before production.
6. **Go-live gates:** validated Float ABI and traces; simulated instruction and amount checks; credentialed Peer preproduction tests for available rails and refunds; approved partner/custody model; qualified review of applicable [FinCEN guidance](https://www.fincen.gov/sites/default/files/2019-05/FinCEN%20Guidance%20CVC%20FINAL%20508.pdf), state laws, [OFAC guidance](https://ofac.treasury.gov/recent-actions/20211015), X Money/other app terms, tax/reporting and tokenized-asset restrictions; audit, monitoring and explicitly authorized low-limit live tests. [X Money](https://money.x.com/en/i/faq) also has its own eligibility and rollout limits.

For the funded flow, verified direct USD through X Money is the first acceptance test. Then verify Cash App and Venmo independently. Preserve funds and retry automatically on no liquidity, no route or outage. Never send to another rail without prior consent.

The web-optimized transparent emblem is in `public/funded-mark.webp`.
